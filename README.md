# AI Incident Parser for R-Vision SOAR

AI Incident Parser — инструмент для автоматизированного анализа и классификации инцидентов информационной безопасности с использованием больших языковых моделей (LLM).

Проект предназначен для интеграции с **R-Vision SOAR** и позволяет извлекать структурированную информацию из неструктурированного текста инцидентов.

На текущем этапе приложение работает автономно: получает текст инцидента из TXT-файла, отправляет его в LLM через API и сохраняет результат анализа в JSON.

## Возможности

- Анализ текста инцидентов информационной безопасности с помощью LLM.
- Автоматическое определение категории инцидента.
- Определение типа инцидента на основании заданного справочника.
- Извлечение объектов и атрибутов из текста инцидента (IP-адресов, имён пользователей, хостов и других данных).
- Контекстная обработка исключений для исключения нерелевантных объектов.
- Использование пользовательских JSON-справочников.
- Проверка структуры ответа LLM и допустимости возвращаемых значений.
- Подключение локальных LLM через OpenAI-совместимый API.
- Сохранение результатов обработки в JSON.

## Архитектура

Обработка инцидента выполняется по следующей схеме:

```text
                  R-Vision SOAR
                       |
                       v
                Текст инцидента
                       |
                       v
                 incident.txt
                       |
                       v
               Python-приложение
                       |
           +-----------+-----------+
           |                       |
           v                       v
     JSON-справочники        Формирование
                             LLM-запроса
           |                       |
           +-----------+-----------+
                       |
                       v
                   LLM API
                       |
                       v
              Контекстный анализ
                       |
                       v
                  JSON-ответ
                       |
                       v
              Проверка результата
                       |
                       v

```

В дальнейшем планируется заменить чтение TXT-файла получением инцидентов непосредственно из R-Vision SOAR.

## Справочники

Для классификации инцидентов и извлечения информации используются четыре независимых JSON-справочника.

| Справочник | Назначение |
|---|---|
| `categories.json` | Допустимые категории инцидентов |
| `incident_types.json` | Допустимые типы инцидентов |
| `data_fields.json` | Поля и объекты, которые необходимо извлекать |
| `exceptions.json` | Условия исключения определённых объектов |

Справочники позволяют изменять правила анализа без изменения исходного кода приложения.

### Категории инцидентов

`categories.json` содержит перечень разрешённых категорий.

LLM должна определить наиболее подходящую категорию на основании контекста инцидента.

Возвращаемая категория должна присутствовать в справочнике.

### Типы инцидентов

`incident_types.json` содержит перечень разрешённых типов инцидентов.

Для каждого инцидента определяется один наиболее подходящий тип.

Возвращаемый тип должен присутствовать в справочнике.

### Извлекаемые данные

`data_fields.json` определяет перечень полей, которые могут присутствовать в итоговом JSON.

Например:

- IP-адрес источника;
- IP-адрес назначения;
- имя пользователя;
- имя хоста;
- доменное имя;
- другие атрибуты инцидента.

Набор полей определяется конфигурацией проекта.

### Исключения

`exceptions.json` содержит правила, позволяющие исключать объекты из результата анализа в зависимости от контекста инцидента.

Пример логики:

```text
Объект: IP-адрес контроллера домена
Условие: инцидент связан с неверно указанным паролем
Действие: исключить IP-адрес контроллера домена
```

Таким образом, модель должна учитывать не только наличие объекта в тексте, но и его роль в конкретном инциденте.

В версии v0.1 смысловая интерпретация исключений выполняется LLM. Дополнительная программная проверка корректности применения всех исключений пока не реализована.

## Установка

### Требования

- Python 3.11 или новее.
- Доступ к LLM через OpenAI-совместимый API.
- Установленный Git (для работы с репозиторием).

### Клонирование репозитория

```bash
git clone https://github.com/Tsutsurin/AI-Incident-Parser-for-R-Vision.git

cd AI-Incident-Parser-for-R-Vision
```

### Создание виртуального окружения

macOS / Linux:

```bash
python3 -m venv .venv
source .venv/bin/activate
```

Windows:

```powershell
py -m venv .venv
.\.venv\Scripts\Activate.ps1
```

```bash
python -m pip install --upgrade pip
python -m pip install -r requirements.txt
```

Для разработки и тестирования дополнительно используются `pytest` и `ruff`.

## Конфигурация

Все настройки приложения находятся в директории `config/`.

В Git хранятся только шаблоны конфигурационных файлов с суффиксом `.example.json`.

Для создания рабочих конфигураций на macOS / Linux:

```bash
for file in config/*.example.json; do
    cp "$file" "${file/.example.json/.json}"
done
```

Рабочие конфигурационные файлы исключены из отслеживания Git через `.gitignore`.

### Настройка LLM

В файле `config/settings.json` необходимо указать параметры подключения к модели.

Пример:

```json
{
  "base_url": "http://127.0.0.1:11434/v1",
  "model": "qwen9B:latest",
  "timeout": 120,
  "max_retries": 2
}
```

Параметры:

| Параметр | Описание |
|---|---|
| `base_url` | Адрес OpenAI-совместимого API |
| `model` | Название используемой модели |
| `timeout` | Таймаут запроса в секундах |
| `max_retries` | Максимальное количество повторных попыток |

Для подключения может использоваться локально развёрнутая Ollama.

При необходимости API-ключ задаётся через переменную окружения `LLM_API_KEY`.

## Запуск

### 1. Подготовка инцидента

Создать файл:

```text
input/incident.txt
```

Поместить в него текст инцидента.

Пример:

```text
Обнаружены множественные неуспешные попытки
аутентификации пользователя test.user.

Источник: 192.168.10.25
Контроллер домена: DC01
IP контроллера домена: 192.168.10.10

Причина: неверно указанный пароль.
Количество событий: 35.
```

### 2. Запуск анализа

Из корневой директории проекта:

```bash
python -m app.main
```

Приложение:

1. Загружает текст инцидента.
2. Загружает JSON-справочники.
3. Формирует запрос к LLM.
4. Получает результат анализа.
5. Проверяет структуру JSON и допустимость значений.
6. Сохраняет результат.

### 3. Результат

Итоговый JSON сохраняется в:

```text
output/result.json
```

Пример ожидаемого результата (при наличии соответствующих значений в справочниках):

```json
{
  "category": "Учетные записи",
  "incident_type": "Неуспешная аутентификация",
  "data": {
    "src_ip": [
      "192.168.10.25"
    ],
    "username": [
      "test.user"
    ]
  }
}
```

В данном примере IP-адрес контроллера домена исключён из результатов в соответствии с контекстным правилом.

## Тестирование

Для проверки корректности работы приложения используется `pytest`.

Запуск тестов:

```bash
python -m pytest -v
```

Текущие тесты проверяют:

- Корректность обработки допустимого результата.
- Отклонение неизвестной категории инцидента.
- Отклонение неизвестного поля данных.

Для проверки качества кода используется Ruff.

Проверка:

```bash
python -m ruff check .
python -m ruff format --check .
```

Автоматическое исправление поддерживаемых замечаний:

```bash
python -m ruff check . --fix
python -m ruff format .
```

## Безопасность

При работе с инцидентами информационной безопасности необходимо учитывать конфиденциальность обрабатываемых данных.

В проекте предусмотрено разделение рабочих конфигураций и шаблонов.

Рекомендуется:

- Использовать локальные LLM или модели, размещённые во внутреннем контуре организации.
- Не публиковать реальные тексты инцидентов.
- Не хранить API-ключи в исходном коде.
- Не отправлять внутренние IP-адреса, учётные записи и служебные сведения в публичный репозиторий.
- Проверять результат LLM перед использованием в автоматизированных сценариях SOAR.

Текст инцидента рассматривается как недоверенный источник данных и не должен изменять правила работы приложения.

## Ограничения текущей версии

Версия v0.1 является прототипом.

На данный момент:

- Источником инцидентов является TXT-файл.
- Интеграция с API R-Vision SOAR не реализована.
- Качество классификации зависит от выбранной LLM и содержимого справочников.
- Корректность смысловых исключений зависит от анализа модели.
- Реализована проверка структуры результата, но не полная независимая проверка всех извлечённых фактов.
- Автоматическое обновление полей инцидента в R-Vision SOAR отсутствует.
